# 场景工作流：把"平的调用链"换成"打包的场景"

维护者的定性（2026-10-02 原话）：「**比如说用户输入的时候：我要新开一个项目，我要你从头到尾审查一个项目，
某个部件（比如button的字有问题）有些问题你帮我核查一下，我要新增一个控件，我要你核查一下这几个对象的问题，
我要深度方向上加上一个对象或者模块，我要重构一个项目（要考虑到xirang的终极设计目的所有都可原子化，终极的
代码复用链等）。每个情况的工具链和workflow都不一样。要用具体场景适当约束工作流，让工作更高效。codegraph的
最大问题在调用链是平的，没有打包的工作流，你能明白我是什么意思吗？一开就直接吞吐整个项目的node,信息驳杂没有
层级，工作流扁平没有场景**」。

## 1. 我们在说什么（把它讲成机制，而不是口号）

**场景 = 一次把「入口 · 层级范围 · 步骤序列 · 停止条件 · 交付物」打包好的工作流。**

平的工具 + 平的调用链 ⇒ 每个问题都要模型**自己把场景重建一遍**。这不是"模型不够聪明"，是**信息没送到**：
它得先猜"用户要的是哪一种活"，再猜"从哪一层进"，再猜"什么时候算完"。

这件事我们**已经在两处吃过亏，并且量到过**：
- 流程表首句是「Read the symptom first」——于是**没有症状的场景**（新开项目）里，agent 的前几次调用是
  注定失败的诊断调用（`check`/`status`）；`new_project` 在表里出现 **0 次**。
- 范围型与症状型两条工作流**已经定过**（见 `0mupw4mzh`），但它们只是流程表里的一句话，**没有名字、没有
  停止条件、没有交付物**；模型仍要自己判断"这属于哪一类"。
- 量出来的代价：`next` 采纳率 **28%**、h2 的 **16 次里 14 次**在决定性事实之前、`status` **8/46** 次
  只是开场收场。

**codegraph 为什么做不到**：它的世界是 `node/edge` 两张平表 + 检索（`explore`/`callers`/`impact`）。
它可以"再检索一次"，但**没有层级可供打包**——没有"面""零件层""契约""槽位"这些可命名的层级，
所以它的每个工作流都只能是"再查一次"。**我们的层级是真的**（`crate → 面 → 零件层 → 契约 → 槽位/切口`），
因此"打包"对我们是一个可实现的工程动作。

## 2. 七个场景（触发判据用**结构信号**，不用关键词）

**过拟合防线**：判据不许是"用户说了哪个词"，必须是**可判定的结构信号**——目录里有没有 manifest、有没有
点名对象、问的是范围还是症状、要"加"还是要"查"、改动落在哪一层。同一场景的**多种措辞**必须落到同一个场景，
这本身就是泛化的机械自证（见 §4）。

| # | 场景（维护者的话） | 结构信号 | 层级 | 步骤序列（我们的工具） | **停止条件** | 交付物 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | 我要新开一个项目 | 目录空 / 无 manifest | crate | `new_project` → `registry` → `check` | 骨架编译过，且出厂面在 `registry` 里 | 可编译骨架 + 面树 |
| S2 | 从头到尾审查一个项目 | 有树 + 问的是**范围**（"有没有别的问题"） | 全树 | `check --census` → **逐栏处置** → 逐栏收紧到 `digest`/`read` | **每一栏都已处置**（要么覆盖，要么写明不覆盖什么） | 逐栏处置表 + 每栏的反证 |
| S3 | 某个部件（button 的字）帮我核查 | 点名**一个**对象/文件 + 症状 | 面 → 函数 | `locate --symptom`/`search` → `read --line` → `why --at` → `check {face}` | 根因（file:line）+ 最小修 + **反证** | 根因 + 行号 + 修法 + 反证命令 |
| S4 | 我要新增一个控件 | "加"一个对象，树已存在 | 面 | `registry`（看同族）→ `apply{add, parent}` → `consistency --specimen` → `check` | 与同族**形状一致**（该有的声明一条不缺）+ 门禁绿 | 新面 + 同族一致证据 |
| S5 | 核查这几个对象的问题 | 点名 **N 个**对象 | N 个面（共享前缀） | `consistency --parent`（**一次**比完同族）→ 逐对象走 S3 | 每个对象都有裁定（含"无问题"也要有依据） | 逐对象表（一次比完，不 N 次） |
| S6 | 深度方向上加上一个对象或模块 | "加深"一个**已存在**的面 | 面 → 零件层 | `explain {node}` → `apply{deepen, inside}` → `check` + 出厂形状钉子 | 树 / 公开路径 / 出厂形状钉子**一个都没动** | 零件层 + "没动树"的证据 |
| S7 | 我要重构一个项目 | "移动/合并/复用"跨对象或跨 crate | 跨 crate | `affected` → `why` 的 plan 半边（作用域/发布）→ `grafts` → `apply` | **全链影响面逐层处置**（每一层：改了什么、为什么不动别的） | 逐层清单 + 迁移记录 |

**七个场景里，今天的流程表只给了 S3 的入口**（"Read the symptom first" + 那句 `apply{deepen}`）。
S1 完全缺席；S2 只有半句话；S4/S5/S6/S7 没有名字、没有停止条件。

## 3. 三个必须一起做的动作

### A. 场景表进流程表（入口）
流程表是**每个 agent 都读的那一页**。把上面七行以"结构信号 → 场景 → 停止条件"的形式写进去，并让第一个
动作就是**判定场景**（判据是结构信号，不是关键词）。这一条是"新能力放进必经路径"的又一次应用。

### B. 答案按**层级**组织（信息不驳杂）
现在是平铺的行；改动是：每条答案标出它**属于哪一层**（crate / 面 / 零件层 / 契约 / 槽位），
并让同一层的相关事实**并进同一行**——这与 `design-mcp-optimization-backlog.md` 的 P0-1/P0-4 和
`design-construction-and-depth-workflow.md` 的 N2 是**同一个机制**（我们已经量到三次"两块事实分居两次
答案"，见 `0muq6opy9`）。

### C. 每个场景一个**停止条件**（不许"看起来查完了"）
S2 的停止条件是"每栏已处置"，S7 的是"逐层影响面已处置"。没有停止条件时，模型只能靠"感觉够了"收手——
那正是 h2 那种"在错的地方找很久"的来源。

## 4. 怎么自证（可机械判定，且专门防过拟合）

1. **场景判定的泛化测试**：对每个场景准备**多种措辞**（含维护者上面那七句的原话 + 同义改写），
   断言它们落到**同一个场景**；再准备两句**结构信号相同、措辞相反**的输入（例如"这个项目是不是从头都是
   对的"vs"帮我从头审一遍"），断言落到同一场景。
2. **停止条件的可判定性**：每个场景的停止条件是**能从产物上读出来的**（`check` 首行、`registry` 的条目、
   `apply` 的回复、逐层清单的条目数），不写"看起来没问题了"。
3. **场景不该改变判据**：场景只约束**路线**，不改任何一条判据（边界、截断说明、拒绝里的形状行一条不删）。
   走得快 ≠ 可以少说。
4. **反证**：故意在某个场景里跳过它的停止条件（例如 S2 只跑 `check` 不做逐栏处置）⇒ 必须能被指出
   "这一栏没被处置"，而不是被当成完成。

## 5. 与其它两份文档的关系

- `design-construction-and-depth-workflow.md` 的 **N1**（建造流程按状态触发）就是这里的 **S1+S4+S6**；
  本文把它扩成完整的场景表，并补上 S2/S5/S7。
- `design-mcp-optimization-backlog.md` 是**卫生**（调用形状、边界、`next`、指纹）；本文是**路线**。
  两者共用同一份底层机制：**把同一层的相关事实并进一次答案**。
- 场景表的**新增**只允许是"结构上可判定的活"，不允许是"某个具体项目的特例"（过拟合三守）。
