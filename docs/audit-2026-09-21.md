## Diagnosis: `kind:` offers no value candidates / `kind:` 值位没有候选

Reported by the user, not part of the four audits. Root cause found and proven;
not fixable without a design change.

**Symptom** (measured on a copy of the user's host, canonical field order):
`kind: |` offers **0** items while `needs_registry: |` and `registry_rule: |`
offer **128**. Field-name completion works at every position (25 items).

**Ruled out, each by experiment**
**逐项排除（各有实验支撑）**

- *The IDE splice*: disabling `__face_fields!` entirely leaves `kind: |` at 0 and
  `needs_registry: |` at 128, so the completion mirror is not involved.
- *The first written field*: reordering the body so `needs_registry` comes first
  keeps the gap attached to `kind` (0) rather than to the first field (128).
- *The dependency shape*: the same asymmetry appears with path dependencies in a
  local copy, so it is not a git-checkout artefact.
- *Field order / separator / trailing comma*: the canonical comma-separated form
  is what was measured.

**Root cause** — rust-analyzer completes inside a macro argument captured as
`expr`, and not inside one captured as `ident` or `ty`. Minimal crate:
`m!{ $k:ident }` → 0 items, `m!{ $t:ty }` → 0, `m!{ $e:expr }` → 124. The face
ladder captures `kind` as `$kind:ident` (line 114 in `__registration_face!` and
five author-facing arms), `preset`/`parts` as `$…:ty`, and every other field as
`expr` — which is exactly the observed pattern.

**Why the fragment cannot simply be changed** — tried and rejected. Capturing
`kind` as `expr` in the author-facing arms fails the moment the value is forwarded
to the internal matcher:

```
error: no rules expected `expr` metavariable
note: while trying to match meta-variable `$kind:ident`
```

rustc turns an `expr` fragment into an opaque, fragment-tagged group that cannot
be re-matched as `ident`/`ty` downstream. Making `kind` completable therefore
means threading an `expr`/`tt` capture through the whole chain
(`__control_object!` → `__registration_face!` → every generated use) and giving up
`kind`'s role as an identifier/type in code generation — or replacing the macro
authoring surface with something an editor can analyse (a struct literal, a
builder, or a proc macro whose fields are typed). Both are design changes, not
bug fixes, so they are left to the user.

**Fixed: the mirror no longer reports errors in the author's editor.** The
editor-only splice used to be a partial struct literal whose fields were typed
`()`, which rust-analyzer rendered *at the macro call site*: one
`expected (), found …` per written field plus `missing structure fields` for the
rest — five red errors in the user's face file. The literal now names every field
with its own type parameter (so written values infer their own types) and takes
the unwritten ones from `..loop {}`, a never-returning base that coerces to the
struct and leaves them open for completion. Measured on a copy of the user's host:
diagnostics **5 → 0**, field-name candidates still **25**.

**已修复：镜像不再在作者编辑器里报错。** 仅供 IDE 的拼接过去是一个字段类型为 `()`
的部分结构体字面量，rust-analyzer 会把它渲染到**宏调用处**：每个已写字段一条
`expected (), found …`，其余字段一条 `missing structure fields`——用户的面文件里因此
有五个红色错误。现在字面量为每个字段命名一个类型参数（写下的值各自推导类型），未写字段
则由 `..loop {}` 提供：一个永不返回、可强制转换成该结构体类型的基值，同时让这些字段继续
获得候选。在用户宿主的副本上实测：诊断 **5 → 0**，字段名候选仍为 **25**。

**Two follow-ups from the user, both fixed.** (1) A face written with `;` or in
another order lost *every* field candidate: the alias's editor splice carries the
author's tokens verbatim, and `FaceFields { kind: Tool; parent: … }` is not a valid
struct literal. The front end now re-emits a normalised splice for the
declarations it handles, so `tool.rs` (semicolons, shuffled) went from 0 to **25**
candidates with 0 diagnostics, while the canonical face is unchanged. (2) The
candidates were bare names, so there was no way to know what to put: every mirror
field now carries bilingual documentation with its meaning, its default and a
one-line example, which the editor shows next to the candidate.

**来自用户的两点后续，均已修复。**（1）用 `;` 或乱序写成的注册面会**丢掉全部**字段
候选：别名自带的编辑器拼接原样携带作者的 token，而 `FaceFields { kind: Tool; parent: … }`
不是合法的结构体字面量。前端现在为它处理的声明补发一份规范化拼接，于是 `tool.rs`
（分号、乱序）从 0 变成 **25** 项候选、0 诊断，规范面则保持原样。（2）候选过去只是光秃秃
的名字，无从知道该填什么：现在镜像的每个字段都带有中英双语文档——含义、默认值与一行示例
——编辑器会把它显示在候选旁边。

**Hint delivered** — the vocabulary hover on `root_object!`/`external_object!` now
says what the user put best: `kind` is the handle-marker type this file declares,
so write the type first and reference it; an editor cannot complete a name the
author has not written, and `kind` is captured as an identifier (not an
expression), which is why no value candidates appear. Verified over LSP: hover
carries the note (1360 characters, field list included).

**已交付的提示**——`root_object!`/`external_object!` 的悬停词表现在说明：`kind` 就是本
文件声明的 handle 标记类型，先写出该类型再在此引用；编辑器无法补全作者尚未写下的名字，
而 `kind` 以标识符（而非表达式）捕获，这正是它没有值候选的原因。已用 LSP 实测：悬停包含
该说明（1360 字符，含字段词表）。

**Third follow-up: the form an editor inserts.** rust-analyzer's macro-call
snippet writes `root_object!($0)` regardless of what the matcher accepts, so the
alias matcher is the delimiter-agnostic token tree (`($($tokens:tt)*)`) and the
front end accepts the parenthesised form. Measurement that matters to an author:
a paren- or bracket-delimited macro call in **item position must end with `;`** —
`root_object!( … );` compiles, `root_object!( … )` does not ("add a semicolon") —
while `root_object! { … }` needs none, because rustc only treats the brace form as
an item. Braces therefore stay the documented spelling; the parens form is pinned
so the editor's snippet cannot silently stop compiling.
**第三点后续：编辑器插入的形式。** 无论匹配器接受什么，rust-analyzer 的宏调用片段
都写成 `root_object!($0)`，因此别名匹配器是与分隔符无关的 token 树
（`($($tokens:tt)*)`），前端也接受括号形式。对作者重要的一条实测结论：位于 **item
位置**的圆括号/方括号宏调用必须以 `;` 结尾——`root_object!( … );` 能编译，
`root_object!( … )` 不行（"add a semicolon"）——而 `root_object! { … }` 不需要，
因为 rustc 只把花括号形式当成 item。因此文档里的写法仍是花括号；括号形式被钉住，
以免编辑器片段悄悄失效。

**Fourth follow-up: the rule is no longer written twice.** A face that owns a
registry had to name its rule twice — `registry_rule_path:` (the file) and
`registry_rule:` (the constant that file defines) — and the second line is always
`<sibling rule module>::REGISTRATION_RULE`, i.e. derivable from the first. It may
now be omitted: the new `face_rule_or!` front end resolves an omitted rule on a
`needs_registry: true` face to the canonical sibling
(`super::registry_rule::REGISTRATION_RULE`), while every other face keeps
`RegistrationRule::ANY` (a child face wants its *parent's* rule, so a permissive
default there is correct). It has to be a proc macro because the canonical
spelling is a *relative* path and `module_path!()` is a string that cannot become
one; measured, tokens built with `Span::call_site()` resolve in the author's
module even when the proc macro is called from a `macro_rules!` body, which is
what makes the relative path work through the whole alias ladder. Studio stops
writing the redundant line back (`derives_rule_from_the_sibling`), the example
host and both READMEs show the shorter form (and no longer import the rule
constant), and a face whose rule was moved off the canonical path still names it.
Pinned by `an_omitted_rule_resolves_to_the_canonical_sibling`,
`a_face_without_a_registry_keeps_the_permissive_default`,
`a_registry_face_derives_the_rule_it_keeps_beside_it`, and the example host's
rule-enforcement tests, which still pass with the field omitted.
**第四点后续：规则不再写两遍。** 拥有注册机的面过去要写两次规则——`registry_rule_path:`
（文件）与 `registry_rule:`（该文件定义的常量）——而第二行永远是
`<同目录规则模块>::REGISTRATION_RULE`，也就是可由第一行推导。现在可以省略：新增的
`face_rule_or!` 前端把 `needs_registry: true` 的面省略掉的规则解析为同目录规范规则
（`super::registry_rule::REGISTRATION_RULE`），其余面保留 `RegistrationRule::ANY`
（子面要的正是**父级**规则，因此那里给宽松默认值是对的）。它必须是过程宏：规范写法是
**相对**路径，而 `module_path!()` 是字符串、无法变成路径；实测表明 `Span::call_site()`
生成的 token 即使由 `macro_rules!` 体调用过程宏，也仍在作者自己的模块里解析——相对
路径能穿过整条别名阶梯正是靠这一点。Studio 不再把这条冗余行写回去
（`derives_rule_from_the_sibling`），示例宿主与两份 README 都改成更短的形式（也不再
导入规则常量），规则被挪离规范路径的面仍然自己写出它。由
`an_omitted_rule_resolves_to_the_canonical_sibling`、
`a_face_without_a_registry_keeps_the_permissive_default`、
`a_registry_face_derives_the_rule_it_keeps_beside_it`，以及示例宿主那些规则约束测试
（省略字段后仍然通过）钉住。

**Fifth follow-up: what the editor inserts, measured.** Two user reports, one
fixed and one refused with evidence.
**第五点后续：编辑器插入什么，已实测。** 两个用户报告：一个修好，一个凭证据说明做不到。

*(1) The macro call inserted `()`.* rust-analyzer builds a macro-call completion in
`crates/ide-completion/src/render/macro_.rs` as `{name}!{bra}$0{ket}`, and
`bra`/`ket` come from `guess_macro_braces`, which reads the macro's
`#[rust_analyzer::macro_style(…)]` **first** and otherwise votes over the macro's
**doc comment** — `vec` gets `[]` because its docs show `vec![]`, while a macro
whose docs never show an invocation gets `()`. Every generated alias now carries
`#[rust_analyzer::macro_style(braces)]` (and so does `external_object!`), because
every face is written with braces. Measured over LSP with the same client and
only that one difference: without the attribute the item is `root_object!(…)`
inserting `root_object!($0)`; with it the item is `root_object! {…}` inserting
`root_object! {$0}` — a snippet with the cursor inside the braces (rust-analyzer
puts a space before `{` by design). rustc accepts the tool attribute without a
warning, so the hint costs nothing at build time.
*（1）宏调用插入 `()`。* rust-analyzer 在
`crates/ide-completion/src/render/macro_.rs` 里把宏调用补全构造成
`{name}!{bra}$0{ket}`，其中 `bra`/`ket` 来自 `guess_macro_braces`：它**首先**读宏上的
`#[rust_analyzer::macro_style(…)]`，否则在宏的**文档注释**里投票——`vec` 的文档里有
`vec![]` 所以得 `[]`，而文档里从不出现调用示例的宏得 `()`。现在每个生成的别名都带
`#[rust_analyzer::macro_style(braces)]`（`external_object!` 同样），因为每个注册面都用
花括号书写。同一客户端、仅此一处差异的 LSP 实测：没有该属性时条目是 `root_object!(…)`、
插入 `root_object!($0)`；有它时条目是 `root_object! {…}`、插入 `root_object! {$0}`
——带 snippet，光标在花括号内（rust-analyzer 按设计在 `{` 前留一个空格）。rustc 接受这个
工具属性且不报警告，因此这条提示不花构建期代价。

*(2) The field name does not insert `: `.* Measured on a **plain** struct in ordinary
Rust (`SCtrl { ki }` → `textEdit.newText = "kind"`), so this is not the mirror:
rust-analyzer's `render_field` inserts `field_with_receiver(…)` — the bare name,
no `: ` edit — and no crate-side attribute changes that; the only callable-related
setting, `completion.callable.snippets`, covers functions and macros, not fields.
The `: ` therefore comes from the author (or an editor-side snippet). What the
crate can do for "what do I put here" is what the field documentation already
does: name, meaning, default and a one-line example per field. In Neovim the
snippet's **trigger is written as `field: `**, because `cmp_luasnip` labels the
item with the trigger: a bare field name would look exactly like
rust-analyzer's own field item and would insert no colon, while `field: ` shows
the colon in the menu and inserts it with the cursor after it (`priority` keeps
it above the bare field inside the snippet source).
*（2）字段名不会插入 `: `。* 在**普通**结构体的普通 Rust 代码上实测
（`SCtrl { ki }` → `textEdit.newText = "kind"`），因此这不是镜像的问题：
rust-analyzer 的 `render_field` 插入的是 `field_with_receiver(…)`——裸名字、没有 `: `
编辑——没有任何 crate 侧属性可以改变它；唯一与 callable 相关的设置
`completion.callable.snippets` 覆盖函数与宏，不覆盖字段。所以 `: ` 来自作者（或编辑器
侧的 snippet）。crate 能为"这里该填什么"做的，正是字段文档已经在做的：每个字段给出
名字、含义、默认值与一行示例。

**Workaround available today** — the field *names* complete everywhere (that is
the `__face_fields!` mirror), and `kind` is the face's own struct name, which the
author has just written; Studio generates it. Values complete for every field
captured as `expr`.

**今天可用的缓解**：字段名在各位置都有候选（`__face_fields!` 镜像），而 `kind` 就是作者
刚写下的那个结构体名、Studio 也会生成它；被捕获为 `expr` 的字段值都能补全。
