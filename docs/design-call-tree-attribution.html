01树的目的不是"好重构",是"归因" why the tree exists

我前几轮把端口/分支方案答成了"重构更方便"——那是次要收益。真正的目的是:

核心命题 出现错误数据时,树要能一次锁定它来自哪里,而不是靠一遍遍复现和猜。

要做到这一点,必须把两个互相独立的维度分开看:

维度问题谁来回答
结果维显示 / 输出对不对?肉眼、测试、runtime_checks
解析维这次调用实际解析到哪个实现?端口索引(构建期)+ trace(运行期)
逃逸的成因 传统调试只能测结果维。所以"在解析维错、在结果维恰好对"的缺陷必然逃逸。

03已落地的一块:端口索引 landed: the port index 已实现 · 门禁通过

本节描述的是已经实现并通过门禁的代码,不是计划。

它编码的四条规则

rule 1
分支句柄 = registry_name,不是路径

B1 与 B2 在 A 处分叉,所以从 B1 里引用 B2 写 B2::port。这就是"根部指分叉处"。

rule 2
绝对解析,与引用位置无关

从 B1 写、从 A2 写,答案相同。这正是调用点与树形状解耦的机制。

rule 3
子树内搜索,分支自身也算

用 lexicon::path_is_under(包含相等);换成严格版会静默丢掉 B2::own 这类分支自身的端口。

rule 4
歧义只报不猜

句柄撞名、端口撞名都列出全部路径。没有"最近祖先优先"——那正是本仓库拒绝的隐性行为。

边界(有意) 同分支内部不需要本索引。分支内部可以直接引用自己的内部(C4::…);封闭的只有边界, 因为要求每次内部协作都先设计一个端口只会增加噪音,不增加保证。
引用示例 从 B1 的子树里引用 B2 的实现 → 写 B2::layout(解析到 C4); 写 B2::C4::… 是穿透,不合法的写法。而 C3 引用 C4 时直接写 C4::…。

载体不是新造的 no new syntax, no new artifact

需求现成的东西位置
"端口"是什么provides:注册面声明对外提供的能力名RegistrationInfo.provides / RegistrationSnapshot.provides
客户端需求requires + missing_capabilitiesregistry_core/requirements/requirements.rs
树里有没有这些数据每个节点保留完整快照RegisteredEntry { info: Arc<RegistrationSnapshot>, child }

所以索引是纯函数:不需要新语法、新落盘工件,也不需要遍历时读文件。

04目标形态:三件事互相咬合 the target shape

4.1 交互:以关注点为中心的局部图 re-centering

我复述的规格:

  1. 搜到文件或 object → 进入;
  2. 默认显示该 object 的调用树,局部展开,不铺满;
  3. 方向键在树上移动选中;
  4. 选中的节点成为新的中心,树围绕它重画(左 = 调用者,右 = 被调用者);
  5. 右侧列出该文件中的函数;
  6. 每个函数显示输入输出,以及它调用了谁。

关键在第 4 条:视图永远是"以关注点为中心的局部调用图",而不是一整棵读不完的树。

4.2 调用面收窄,观察面完整 closed boundary, complete tree

调用面(caller)
跨分支只能写 Branch::port

A1::B1::… 这类穿透写法不合法。替换一个分支时调用方零改动。

观察面(observer)
整棵树仍可被渲染器还原

树是给观察者的,端口是给调用者的。两者不冲突——这正是"渲染器还能还原整棵树"确认掉的那个张力。

5.2 缺的 this is what "表达还是有问题" means

#缺口说明
①居中语义未确认 待你定方向键是"只挪光标"还是"把选中节点变成新中心重画"?图的按键处理不在 keyboard.rs,我尚未定位到,因此不能替你断言。这是交互核心。
②右栏是"字段",不是"函数 + 输入输出 + 调用了谁"今天 search_detail.rs 用 search_field(name, value, query) 渲染选中行的字段。要的形态需要把 source_index(函数列表)+ trace 的 locals / data edges(输入输出)+ graph_queries(callees)接起来——三样都在,只是没接线。
③展开策略未定 待你定"不用全部显示出来"需要一条明确规则:限深度?按选中逐层展开?只展开有值的分支?这是设计参数,决定视图在真实大树上还能不能读。
④归因维完全缺席 1.x边没有"解析到哪个实现"的标签;函数的输入输出没有"值来自哪一跳"。完整 trace ingest 被仓库明确记为 1.x(docs/design-trace-ingest.md),1.0 只保留示例标注 + 一条回归测试。提前是一次范围决定。
证据:为什么说"模型对了、表达链断了"

docs/design-trace-ingest.md 记录:render_tree、render_provenance、 render_data_flow、render_call_report_for_trace 四个渲染函数全仓没有任何调用者; 没有任何东西序列化 trace;示例 trace 是惰性的(不记录 locals),所以 DATA 面板一直渲染空状态。

也就是说:帧(FrameRecord/FramePath/FrameView)、局部值、来源边 (DataEdge/DataHop)这些模型都在,断掉的是"记录 → 对照 → 呈现"这条链。

06为什么这几层合起来能"一次锁定" why the layers compose

意图
声明:本意是 relative
② 静态解析
构建期解析每个引用 → 直接报 "Slider 解析到 physical,与本意不符"
Slider / Timeline 在跑起来之前就被点名
③ 变更报告
替换 / 嫁接改变解析 → "Button 的 coordinates 现解析到 X(此前 Y)"
④ 运行期
每次调用记 (port, 实现身份, 值 + 来源) → 两条并行链按同一 port 对齐并排渲染

任一层单独都不够:静态层抓"逃逸类",运行期层抓"值来源",变更层抓"被悄悄改掉"。 合起来才是不看结果对不对,直接看解析分叉——也就是"一次锁定问题"。

07待确认 open questions

1

居中语义:选中即居中,还是需要确认键?

我的倾向:选中即居中(方向键每次移动都重画),因为它让"以关注点为中心"成为默认而不是操作。
2

展开策略(缺口 ③)

我的倾向:按选中逐层展开 + 一条深度上限;上限是参数而不是硬编码。
3

意图口径 A / B

A = 每个消费者各自声明要哪个提供者;B = 分支级策略"本分支内 coordinates 一律 relative"。
我的倾向:B。你的"本意"是框架级约定,且 B 让新增消费者自动受约束——A 会漏掉新加的消费者,而那正是逃逸的成因。
4

范围:④ 的完整 trace ingest 要不要提前到 1.0 之前?

我的倾向:先 ①②③(不用运行、复用已有数据,已能抓住逃逸类),④ 按 1.x 的节奏。

08这次我没有做的事 deliberate non-scope

  • 没有动渲染器(pub use child::* → 只发声明端口)。它是收窄所有宿主可见性的破坏性改动, 且你已说明"渲染器还能还原整棵树",所以它可以等,而且应该和示例一起改。
  • 没有动 trace 的任何记录路径,也没有动 Studio 的界面。
  • 没有新增任何落盘工件:义务清单 / 解析报告都应该派生,否则会变成第二个事实来源。
