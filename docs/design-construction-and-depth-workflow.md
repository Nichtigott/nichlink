# 建造与纵深修改：xirang 的核心优势应当被量出来

维护者的定性（2026-10-02 原话）：「**当有一个项目开始的时候是有工作流的：就和素描一样，先是大的角色对象的
模块组织，（分crate的时候我的xirang的机制是如何的）然后是大角色中的小角色是如何组织的，让ai可以参与到
前期的项目构建中，在前期形成优秀的架构设计，并且能用规范约束ai的文件内的组织逻辑，让整个项目的代码质量
提高，逻辑清晰，层层提升，层层都可以修改，甚至我的截断就是为了让深度方向上的修改能更加快速地落实（比如
我要改内核中的某个算法），会从整个代码调用链上进行层层的设计跟进，稳稳锁定设计目标等，不跑偏。这是我们的
核心优势**」。

`design-mcp-optimization-backlog.md` 那一份优化的是**诊断代价**（调用数、token、信息形状）。它是对的，但
它是卫生，不是战略。**战略在这条轴上，而 codegraph 在这条轴上永远无法竞争**：它读的是**已经存在**的代码，
没有准入路径、没有规则、没有脚手架、没有替换点。

## 1. 今天有什么（查实，不是印象）

| 层 | 机制 | 在哪 |
| --- | --- | --- |
| crate 划分 | `new_project` 走 `build_time::scaffold::create_project`——与 CLI 的 `xirang new`、Studio 向导**同一份**渲染 | `apply.rs` / `new_project.rs` |
| 大角色（面） | `apply {action: "add", parent: …}`——写入经**内核准入 + 父面规则 + 拓扑检查** | `apply.rs` |
| 小角色（面内） | `apply {action: "deepen", node, inside}`——把零件层写进那个面**自己的文件**，不动树、公开路径与出厂形状钉子 | `apply.rs` |
| 字段/契约 | `apply {action: "edit", fields}`；面携带的 `///` 契约行是它的承诺 | `apply.rs` |
| 规范 | **父面规则 + 准入 + 拓扑检查**（宿主面自己的）· `requirements`（能力声明） | `kernel/src/registry_core/` |
| 可替换边界 | `grafts`：外部 graft 计划 × 宿主 `static_graft_plan!` 的槽位声明 | `grafts.rs` |
| 发布作用域 | entry plan / scope / pruning（哪些进发布、哪些只在构建里被发现） | `why` 的 plan 半边 |
| 本检出自己的规范 | `conventions`（尺寸棘轮、测试形状、挂载规则、双语文档…） | `conventions/`（`publish = false`，**走检出**，宿主项目用不上） |

**一个必须纠正的误认**：`registry_rule` **不是内核模块**，它是 h2 夹具树里长出来的面。内核里没有它。
所以"规范约束"今天真实存在的只有**父面规则 + 准入 + 拓扑检查**这三样，作用在**注册面这一层**。

## 2. 缺口（按维护者的词汇）

### G1 阶段没有入口 —— "素描的第一层"进不去
流程表首句是「Read the symptom first」，`new_project` **0 次**、`scaffold` **0 次**。
空目录上没有症状可读 ⇒ agent 的第一批调用是**注定失败**的诊断调用（`check`/`status`），而不是"先立骨架"。
**这是"新能力没有放进必经路径"的又一次现身**，而且这次缺的是**整条工作流的入口**。

### G2 纵深修改没有"逐层跟进清单"
"改内核中的某个算法"要同步的东西今天分散在六处：本层契约行（`read`/`digest`）· 同族兄弟（`consistency`）·
父面规则（准入）· 依赖它的面（`affected`）· 发布作用域（`why` 的 plan 半边）· 钉住它的测试（`check` 的
test-reachable 栏）。**没有一次调用给出"这条链上每一层分别要做什么"**。
这正是我在 W8 里量到三次的"两块事实分居两次答案"（分支栏 × 契约行、`read × digest`、`search × read`）——
只不过这一次它落在**核心优势所在的地方**。

### G3 "面内组织逻辑"的规范无法声明
`deepen` 只是一个**动作**，不是一条**规范**：宿主项目不能声明"这一族面必须有哪些零件层 / 哪些字段 / 哪些
契约行"，因此也就没有东西能在 `check` 里拒绝一个不合规的面。`conventions` 管的是**本检出自己**，宿主用不上。
⇒ 维护者说的"用规范约束 ai 的文件内组织逻辑"，目前**只能靠 agent 自觉**。

### G4 深度上的"可改点"与 graft 的关系没讲清
`grafts` 替换的是**面或子树**（横向的边界）；`deepen` 写进去的**零件层**是纵向的。今天没有一句话说明
"要在深度上留一个可改点，应当怎么做"，也没有工具检查"这个零件层是否被某个 graft 覆盖/绕过"。

## 3. 待做（每条都要求可机械自证）

### N1 建造流程按**状态**触发（G1）
流程表加一条建造工作流，入口由**这棵树处于什么阶段**决定，而不是由 agent 猜：
无 manifest ⇒ `new_project`；有 manifest 无面 ⇒ `apply{add}`；有面 ⇒ `apply{deepen}` / `fields` / `registry`。
**自证**：在**空目录**上，agent 的第一次工具调用应当是 `new_project`（今天是 `check`/`status` 这类注定失败的
调用）——这是可测的，且不需要外部测试。

### N2 一次调用给出"纵深跟进清单"（G2）
新读工具（或 `affected` 的扩展）：给"改这里 ⇒ 每一层要动什么"，六层逐条：本层契约行 · 同族兄弟 · 父面规则 ·
依赖者 · 作用域/发布 · 钉住它的测试。
**自证（含反证）**：改内核一个函数后一次调用列出全部六层；**故意漏一层**（例如不同步兄弟、或不动那条契约行）
⇒ 清单必须点名它。这一条同时就是"不跑偏"的可判定形式。

### N3 宿主可声明的组织规范（G3）
让宿主项目声明"这一族面必须有哪些零件层/字段/契约行"，并由 `check`/`conformance` 强制（不能放进
`conventions`——它 `publish = false` 且走检出）。
**自证**：造一个违反声明的面 ⇒ 门禁红且**点名**缺哪条；合规的面 ⇒ 绿。

### N4 深度可改点（G4）
把 `deepen` 写出的零件层与 graft 槽位挂钩：一个零件层可以被某个 graft 计划点名替换/绕过，`grafts` 报出它。
**自证**：给一个零件层声明 graft ⇒ `grafts` 把它列为可替换点；撤销声明 ⇒ 回到不可替换。

## 4. 这条轴该怎么量（判据与诊断轴不同）

诊断轴的判据是"调用数/token"。**建造轴的判据必须是"结构质量"**，否则我们会优化错东西：

1. **首次产出可编译骨架的调用数**（从空目录到 `check` 绿、`conventions` 绿）。
2. **规范违例数**（N3 之后：声明的组织规范被违反几次、是否被门禁抓到）。
3. **纵深修改的层次覆盖率**：改了该改的层 / 没动不该动的层（**附带损伤**＝无关面被改动的数量）。
4. **跑偏率**：同一目标在 N 次修改内是否被锁定（可判定形式：修改后的树是否仍满足那道题声明的作用域与
   出厂形状钉子）。

**四栏（收敛/反复/截断/失败）与三轴 token 在建造轴上依然量，但它们是次要的**——建造期的浪费是"骨架错了
再返工"，不是"多问了一次"。

## 5. 与诊断轴的关系（别把两份清单混起来）

- `design-mcp-optimization-backlog.md` 的 P0–P2：**继续做**（便宜、有测量依据），但把它当**卫生**。
- 本文的 N1–N4：**战略**。其中 N2 与 P0-1/P0-4 是同一个洞（两块事实分居）的三个面，**修法应当共用一份
  "把同一层的相关事实并进一次答案"的机制**，而不是三处各写一遍。
- 语料（P2-2 的真实社区 bug 反向注入）**只覆盖诊断轴**。建造轴需要**自己的题**：给一个目标描述，看它立出的
  骨架是否 (a) 可编译 (b) 层数正确 (c) 规范零违例 (d) 一次纵深修改的层次覆盖正确。
