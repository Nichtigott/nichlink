# 深度分析：非桥为什么占 84% · 4.5× 从哪来 · "整体比 codegraph 好"缺什么

**维护者的判断**（原话意）：mcp 无非几件事——**工作流优化**（真实工程场景：新建项目等；以及**工程链路**：
稳定写法形成统一规范要求 · 项目初期就有**示例代码约束** · 关于示例代码/公共 API 设计/架构（目录）设计的强约束）
· **工作流优化的本质**是"让 ai 知道什么时候调用什么工作流，而不是所有都跑一遍"（不必外接模型，代码场景就那么多种）
· codegraph 看起来好是因为**命令极少（甚至只有一个）**，但**信息太多会导致幻觉** ⇒ 所以要用工作流。
并问：**"4x、非桥这些为什么会有这么多……效果为什么这么差"**。

## 一、先分清"效果"与"代价"（我实测的，不是判断）

| 面 | 数 | 结论 |
| --- | --- | --- |
| **正确性（效果）** | 26 题**变差 0** ✓ · 四道 hardbug **4/4 对** ✓ · 第八轮作废那 11 道 **11/11 对** ✓ | **不差** ✓ |
| **代价（token）** | 26 道合计缓存读 **0.56×** ✓ · 切面（11 只读题）**0.061×** ✓ | **答辩型：好得多** ✓ |
| **代价（四道 hardbug 这一类）** | 步数 **1.9×** ✗ · 缓存读 **4.5×** ✗✗ | **猎取型：差** ✗ |
| **过程** | 桥调用接近理想（4/5/3/2 vs 理想 1/2/1/2 ✓），但**非桥结果占该窗口 84%** ✗ | **差在"桥之外那一圈"** ✗ |

⇒ 所以"效果差"要拆成两句：**答得对，但那一类题的"做"很贵** ✓；而**贵的部分几乎不在桥里** ✗。

## 二、非桥 84% 到底是什么（实测：`bash` 26 次 · `read` 9 · `write` 7 · `edit` 3）

四道 hardbug 窗口内的非桥调用，逐条看（会话原文 ✓）：
- **`cargo test` 若干次**（含在 `/tmp` **另起一次构建**做"改一处 ⇒ 变绿"的反证 ✓）——**整段输出进上下文** ✗；
- **`grep -n '' src/control/object/*/*.rs`** —— **一次把所有兄弟的源码 dump 进上下文** ✗✗（而 h1 的配方明写
  "**必须拒绝：逐个读完再猜**" ✓：臂没有"猜"✓，但它**也读了** ✗）；
- `sed -n` 切片、`python3` heredoc 探针、`edit/write` 改文件 ✓。

⇒ **这 84% 不是"我们的桥话多"，而是"这一圈活没人管"** ✓：**改 → 构建 → 测试 → 观察 → 反证**这一圈，
今天**全靠 agent 用裸 shell 自己搭** ✗，而它每一步的输出都被**每一轮重发**（成本是乘数 ✓）。

## 三、结构原因（我的判断，有证据支撑）

**我们的桥是一张"问答面"，不是一份"工作流"。** 18 个读工具 + 一条预览式写路径 ✓，每个都答得好
（有界 · 自报不完整 · 带 `next` ✓）；但**"这一圈接下来该做什么"没有任何东西持有** ✗：
- 流程表是**散文**（"结构信号 → 入口调用 → 停止条件" ✓），要 agent 自己**解读并执行** ✗；
- 每条答案的 `next` 行只指**下一步的一次调用** ✓，不持有**多步状态**（第 k 步、做完检查什么、何时收工 ✗）；
- 本仓已经量过一条硬事实：**独立命令式的兜底代理不会主动调**（第五轮 `--list` 实际调用 **0 次** ✓）
  ⇒ 凡是"写在旁边、不进必经路径"的指引，等于没有 ✗。

⇒ 于是**工作流的成本落在 agent 的思维链里** ✗（这与你说的"工作流优化"是同一件事的另一面 ✓）：
它得自己攒出"先 `check` 定位、再 `apply` 改、再 `check` 验证、再构造反证"这一串 ✓ —— 攒得出来（所以答对了 ✓），
但**攒的过程与那圈 shell 的输出，全在桥外计费** ✗✓。

**为什么 codegraph 在那一类反而省** ✗：它**命令少、答案大**（一次 dump 整个文件/图 ✓）⇒ **轮次少**（13 vs 25 ✓）、
agent 的"攒流程"负担小 ✓；代价是**信息无边界、易幻觉** ✗（你的判断 ✓），但那类题恰好**要多读原文** ⇒ 它的短处
不发作、长处发作 ✓✓。**它的便宜不是因为它更聪明，而是因为它把"读"这件事一次做完了** ✓。

## 四、"整体比 codegraph 好"缺的三块（对着你的框架说）

1. **工作流要成为"可执行的东西"，不只是散文** ✗✓：S1–S7 的分层/停止条件已经在 `docs/design-scenario-workflows.md`
   写好 ✓，但它们是**文档** ✗。要变成**必经路径上的通道**：一次调用给出"**这一步用哪个工具 · 做完看什么 · 下一步是什么 ·
   什么时候停**"（并且随任务推进变状态 ✓），而不是等 agent 读散文自己拼 ✓。
2. **工程链路**（你说的积累层）：① **示例代码约束**——桥里已有雏形（`consistency --parent|--specimen` 比同族 ✓），
   但缺**"新代码必须沿用哪一段示例"**的通道 ✗；② **公共 API / 目录设计**的规范——本仓有 `conventions` 与父面规则
   (`registry_rule`) ✓，但**那是本仓自己的**，宿用项目**用不上** ✗ ⇒ 需要一个**宿主可用的规范层** ✓；
   ③ **稳定写法成规范**（工程积累）= 把"已经稳定的写法"变成**可检查的约束**并让新代码对齐 ✓ —— 这正是
   "一条规则一份实现"从**内核**扩展到**宿主工程** ✓。
3. **"少命令"的正确形态**：不是少给能力，而是**每个场景一个入口** ✓。codegraph 的"一个命令"胜在
   **没有选择成本** ✓；我们的 18 个工具胜在**有界** ✓ ⇒ 合成起来是**按场景打包、按步骤给**（你说的
   "让 ai 知道什么时候调用什么工作流，而不是所有都跑一遍" ✓✓），而不是"再压答案长度" ✗。

## 五、可度量的目标与证伪（写死，免得自说自话）

第十轮（同一批 26 道题，对照继续复用冻结结果 ✓）要看的**不是总量**，而是三件：
1. **四道 hardbug 的"非桥字节占比"**：84% → **≤60%** ✓（预测已在 `next-five-expected-effect.md` 登记 ✓）；
2. **那四道的缓存读**：4.5× → **≤2.5×** ✓；
3. **正确性不许掉**：4/4 仍对 ✓，且 26 题仍**变差 0** ✓。
**若 1 不降**：说明"指路"没进必经路径 ✗（本仓已有先例：`--list` 0 次调用 ✓）⇒ 问题在通道，不在措辞 ✓；
**若 1 降而 2 不降**：说明省下来的字节不是那几块大的 ✗ ⇒ 归因错，重查 ✗；
**若效果掉了**：说明砍错了东西（比如把反证砍了 ✗）⇒ 回退并用判据换数字的错 ✓。

## 六、落成条目（T-32：场景入口即工作流状态）

**判据**（先登记，实现前不改）：
1. **一次调用给出"这一步"**：入口 = 场景名（S1–S7 见 `docs/design-scenario-workflows.md` ✓），回复必须同时给出
   **① 这一步用哪个工具 · ② 做完看什么（可核对的判据）· ③ 下一步是什么 · ④ 什么时候停** ✓；
2. **状态由产物决定，不由会话记忆决定** ✗✓：下一步从**树的现状**读出来（有没有面 · 有没有构建产物 ·
   有没有台账条目 · 有没有未采信的路线 ✓），这样换一个 agent、换一个会话，工作流仍然接得上 ✓
   ——这正是本仓既有的"停止条件必须能从产物里读出来"（T-11 ✓）的延伸 ✓；
3. **不新增第二个实现** ✗：入口只做**编排**，每一步仍调既有工具（渲染/准入仍走内核 ✓）；
4. **反证**：把某个产物状态改掉（例如删掉构建产物 / 加一条台账）⇒ 同一个入口给出的**下一步必须变** ✓；
5. **度量的靶子**：四道 hardbug 的**非桥字节占比 ≤60%** ✓ 与**缓存读 ≤2.5×** ✓（第十轮；同一批题、对照复用 ✓）。
**与"信息多导致幻觉"的关系**：这是**有界**的方向——每一步只给该步需要的（其余用 `next` 指路 ✓），
而不是像 codegraph 那样一次 dump 全部原文 ✗✓。
