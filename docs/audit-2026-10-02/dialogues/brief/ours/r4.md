# r4 — 注入缺陷 4（validation-trap）
**① 症状** `cargo test --offline` 恰 1 条红：`a_zero_entry_is_not_postable`
（tests/ledger.rs:38，`left: Some(0)` / `right: None`，exit 101）。
**② 根因** `src/model/entry.rs:39`（`Entry::postable`）：`self.has_receipt || self.amount == 0`。
契约在 :30-37——「has_receipt 且金额非零才可入账；零金额分录**一律不可**入账，调用方依赖这个拒绝」；
`||` 把两个条件写成**析取**：零金额分录即使没有凭据也被判可入账，且无凭据的分录（amount≠0）也被误判可入账。
`Store::post`（src/store/memory.rs:22-27）把 `postable()` 当唯一的入账守卫，于是零金额分录被真的推入
`entries` 并返回 `Some(0)`——这与 `an_entry_without_a_receipt_is_not_postable` 依赖的「拒绝」相反。
**③ 最小修** `src/model/entry.rs:39`：`self.has_receipt || self.amount == 0` → `self.has_receipt && self.amount != 0`（1 行，
即契约的字面转写）。改后 `cargo test --offline`：`test result: ok. 9 passed; 0 failed`，exit 0。
**④ 反证** 能证伪本诊断的观察：①若系统里还有第二道拒绝（例如 `Store::post` 自己再判一次），这一行写错也不会红——
`callgraph {postable}` 给出唯一调用者 `Store::post`，其 :23 只看 `postable()`，且 :26-27 直接 push ⇒ 无第二道；
②若这一行与红无关，改回 `||` 不会重现红。实际做：改 1 行 → 全绿；再还原成 `||` → 只跑该条仍红
（同 left Some(0) / right None）⇒ 该行是唯一充分原因；还原修复后再次 9 passed。
