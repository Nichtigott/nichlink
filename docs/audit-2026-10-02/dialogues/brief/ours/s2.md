## 交付答案（逐字）

# s2 — 全绿但有一个面是红的，是哪个面
**① 症状** `cargo test --offline`（默认面）全绿；但**有一个面是红的**：`ledger-core` 的 `audit` 特性面。
只读，未改动。
**② 结论（文件:行号）** 红的面 = **feature `audit`**（`cargo test --features audit`，等价名 `--all-features`）：唯一失败
`crates/core/tests/audit.rs:24-28` 的 `the_audit_counts_the_non_zero_entries`
（panic 在 `crates/core/tests/audit.rs:24`：`assertion left == right failed: the zero entry is not counted`）。
根因在 `crates/core/src/audit.rs:9`：`entries.iter().filter(|entry| entry.amount == 0).count()`
——计数谓词写反，数与测试（:16-18 的注释：零那条不计入）要求相反。
**③ 为什么默认面全绿（机制一句）** `crates/core/src/lib.rs:8-9` 用 `#[cfg(feature = "audit")]` 门控 `audit` 模块，
`crates/core/tests/audit.rs:10` 又有 `#![cfg(feature = "audit")]`：默认面**根本不编译这两者**
（6 个测试二进制全 ok，其中 4 个是 `0 passed`），于是红的证据只存在于特性面。
**④ 证据** `check {face:default}` → `verdict passed (cargo exit 0)`；
`check {face:audit}` → `verdict failed (cargo exit 101)`，`failed the_audit_counts_the_non_zero_entries`，
log `…/s2/target/nichlink/out/check-audit.log`；`check {face:all}` → 同一条红。
`status` 的面表已给线索：`faces ledger-core: default=[] all=[audit]`。
**⑤ 反证** 若「红的面」是默认面，`check {face:default}` 会是非 0；实际它 exit 0。若默认面之所以绿是因为
修复存在，`--features audit` 也该绿；实际它仍红 ⇒ 默认面的绿是**没跑**（0 passed），不是没失败。
**⑥ 调用清单（`target/round9/logs/s2.jsonl`）** - `check {face:default}` — passed，cargo exit 0，7 个二进制全 0 failed。
- `check {face:audit}` — failed，cargo exit 101，点名该测试与 panic 位置。
- `check {face:all}` — failed，同一条红（特性合流后仍只这一条）。
总调用：成功 3 / 被拒 0
