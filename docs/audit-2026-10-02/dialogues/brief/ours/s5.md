# s5 — 渲染缺了什么
**① 症状** `check {face:default}` → `verdict failed (cargo exit 101)`；渲染面 3 条红，其中两条的 panic 文本就是渲染输出：
`:38` `the count line is printed`、`:48` `the count block is written: LEDGER REPORT`（`crates/report/tests/report.rs`）。
只读，未改动。
**② 结论（文件:行号）** 渲染**缺的是「条数块」那一行 `entries: {n}`**：`crates/report/src/render.rs:7-13` 的 `render` 只写表头
（`:8`）与逐条分录（`:9-11`），**从未调用** `write_count`（定义在 `crates/report/src/render.rs:17-19，
体内 `:18` 正是 `entries: {}\n`）。契约在 `crates/report/src/render.rs:5-6`：
a header, **the count**, then one line per entry／表头、**条数**，然后每条一行 ⇒ 实现在「表头」与「分录」之间漏了条数块。
（同树还有一条**与渲染无关**的红：`the_minimum_amount_filter_keeps_the_entries_at_or_above_it`
（`crates/report/tests/report.rs:27`）— 由 `crates/report/src/query.rs:27` 的 `entry.amount > min` 反转引起，
不是渲染缺件，单列以免混淆。）
**③ 证据** `callgraph {function:render}` → `callees: from, push_str`（**没有** `write_count`），`also here: write_count -> render.rs:17`；
`read {path:crates/report/src/render.rs, whole}` → 8-13 行逐字打印，条数块不在其中；
`check` 的 `why` 行直接给出缺件的症状原话（`the count line is printed` / `the count block is written`）。
**④ 反证** 若「缺的」是别的（例如表头或某条分录），`render` 的输出里会少别的行；实测缺的恰是
`text.find("entries: 3")` 找不到（:38）且 `contains("entries: 3")` 为假（:48），而 `LEDGER REPORT` 与
`a: -500`/`b: 5000` 都在（:47/:49 通过）⇒ 少的是条数块这一行，不是别的。若渲染其实调了 `write_count`，
`callgraph` 的 callees 会带它、这两条测试也不会红——两处都不支持那种读法。
**⑤ 调用清单（`target/round9/logs/s5.jsonl`）** - `check {face:default}` — failed，cargo exit 101，3 条红逐条点名（含过滤那条）。
- `callgraph {function:render}` — callees 无 `write_count`；`also here` 指向 :17（本树 `write_count` 定义处）。
- `read {path:crates/report/src/render.rs, whole}` — 8-13 行渲染体与 18-20 行条数块定义。
总调用：成功 3 / 被拒 0
