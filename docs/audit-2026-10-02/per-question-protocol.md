# 逐题协议（一题一会话）· 第十轮跑法记录

**这份文件是"怎么跑"的唯一入口**：装置布局、任务书、token 读法、两侧同口径、纪律、以及每题的会话 id 表。
装置脚本：`tools/xirang-perquestion-protocol.py`（子命令 `setup` / `brief <arm> <id>` / `measure` / `sessions`）。

## 0. 为什么换成一题一会话

第九轮是"26 题挤一条会话"，由此产生三个**在构造上**无法修复的问题（都被实测撞到）：

1. **逐题 token 切不出来**：两臂都在会话开头做跨题批扫（`for id in …; do ./cg.sh "$id" …; done`），之后用 `cd` 后的相对路径干活
   ⇒ 任何"按题归属"的切法都是**假的**（第九轮的逐题表就是这么坏掉的：cg 的一批调用被判进装置桶，那些题显示 `0/0/0/0`）。
2. **整轮不可比**：两侧回合结构不同（我们 1 个 turn 含收尾，cg 4 个 turn 其中一个是改正任务）⇒ 旧的"整轮 0.940×"是混合口径。
3. **答案形状被会话顺序污染**：后答的题能"顺手用上"前一道题的结论。

⇒ **一题一会话**之后：每一题的 token 就是**那个会话自己的 `usage` 合计**，**不需要归属切分**（这正是维护者说的"程序本来就有记录"）。

## 1. 装置布局

```
target/round10/
  ours/  trees/<id>/      26 份独立副本（内含 carrier/）+ logs/<id>.jsonl + answers/<id>.md
  cg/    trees/<id>/      同上（cg 在自己副本里建索引，可写）
  briefs/<arm>-<id>.md    52 份任务书（生成即冻结）
```

- **副本制备**：`setup` 子命令从 `target/round9/trees/` rsync（排除 `target/`、`.codegraph`、`.git`），
  `g1` ≡ `s3`、`g2` ≡ `s5` 各拷一份**独立副本**（一题一棵树），`carrier/` 供 `fa`/`fb`/`fc`/`g3` 的 `../carrier/control-button-graft` 解析。
- **制备后必须逐棵复算 sha256 对回 `TREES.json`**（算法：跳过 `{target,.codegraph,.git}`、按相对路径排序、
  `update(rel) │ 0x00 │ update(len) │ 0x00 │ update(bytes) │ 0x00`）；两臂各 26/26 通过才开跑。
- **开工前还要确认原树是题目态** —— 实测过两次的坑：**臂做完题会改树，那个态不是题目态**
  （第九轮 11 棵"与登记不符"的真因就是上一臂的交付态没还原）。

## 2. token 读法（两侧同一把尺）

`usage` 是**每步的增量**（`inputTokens` = 未命中输入 · `cacheReadTokens` = 缓存读 · `outputTokens` = 输出；
`cacheWriteTokens` 本装置恒为 0）。一题一会话 ⇒ **该题的用量 = 该会话所有 `assistant/message` 的 usage 求和** ✓。

- **要不要"做差"**：只有当你想把**同一条会话**切成两段（例如"答题段 vs 装置段"）时才需要在两个时刻的
  **累计值上做差**；一题一会话的整题用量**直接求和即可**，不需要任何归属规则。
- **两侧同字段、同求和规则**；**codegraph 的索引成本（`init`）单列**（它需要可写树 + 建索引，我们的桥不需要）。
- 推理字符：`content[type=="reasoning"]` 的字符数和（同一字段，两侧一致）。

## 3. 纪律（写进 52 份任务书，两侧逐字相同）

- 答案固定五段形状（症状 / 根因`文件:行号`+机制 / 最小修 / 反证 / 调用清单）+ 末行 `总调用：成功 N / 被拒 M`。
- **禁令**：不许读 `target/round7|round8|round9` 下的任何答案或日志；不许 `git log/show` 查题树历史；
  断言"某条路径"必须每跳回源码核过（不许由命名推断）。
- **只读题**（`s1`–`s8`/`g1`/`g2`/`g4`）不许改树；**可改题**交付后 `cargo test --offline` 必须绿。
- **装置问题自报**：树不对、工具异常 ⇒ 写 `answers/APPARATUS-<id>.md` 并说明。
- **会话可寻址**：每份任务书首行是探针串 `ROUND10 <arm> <id>` ⇒ `measure` 靠它在会话目录里**精确定位该题的会话**。

## 4. 谁在跑：AgentTeams，成员上限 8 ⇒ **分 7 批轮换**

"一题一会话"在 AgentTeams 上的落地：**一题一个成员**（成员的会话就是那一道题的会话）。
平台的硬限制是 **`maxMembers = 8`** ⇒ 52 题（26 × 2 臂）分 **7 批**，每批 8 人（最后一 4 人），
**成对编批**（同一道题的两臂在同一批里跑，保证两侧条件一致）：

| 批 | 题号 | 臂 | 人数 |
| --- | --- | --- | --- |
| `xirang-r10-b1` | `r1`–`r4` | ours + cg | 8 |
| `b2` | `s1`–`s4` | ours + cg | 8 |
| `b3` | `s5`–`s8` | ours + cg | 8 |
| `b4` | `g1`–`g4` | ours + cg | 8 |
| `b5` | `h1` · `fa` · `fb` · `fc` | ours + cg | 8 |
| `b6` | `fd` · `fe` · `h1-supply-chain` · `h2-claim-unkept` | ours + cg | 8 |
| `b7` | `h3-cross-file-chain` · `h4-one-file-many-algorithms` | ours + cg | 4 |

跑法纪律（都在任务书里，两侧逐字相同）：一题一条任务、assignee 就是那个成员、**无依赖**；
成员做完 `update_task(status=completed)`；一批全终态后再起下一批（成员不做第二题 —— 否则就退化成多题一会话 ✗）。

## 6. 收数

`measure` 逐题打印：会话 id · 步 · 未命中输入 · 缓存读 · 输出 · 推理字符 · 仪器调用数，并给出**两臂合计与命中率**。
因为没有归属切分，这张表**每一格都是该题自己的数**（这也正是它比第九轮那张表更该被引用的原因）。
