### `board_object!` 是什么（给他的那份解释，留档）

从 `/tmp/xirang-lab/dash` 的生成树里取的原文：

```rust
// target/debug/build/dash-7d8fb52fc37f99a2/out/generated_lib.rs:30
macro_rules! board_object {
    ($($tokens:tt)*) => {
        ::xirang_toolchain::__xirang_object! { $($tokens)* }
        #[cfg(rust_analyzer)]
        ::xirang_toolchain::face_fields_mirror! { $($tokens)* }
    }
}
```

1. 它是**构建期生成的一条薄转发宏**，写在生成树里（`include!(OUT_DIR/generated_lib.rs)`），不在宿主源码里；
   转发到唯一的隐藏实现 `__xirang_object!`，另给编辑器补全挂一份 `face_fields_mirror!`。
2. **每个"拥有注册机的面"各有一条**：那棵树里是 `root_object!` / `board_object!` / `input_object!`
   （`renderer/aliases.rs` 的 `render_object_aliases` + `visit_object_aliases`：`names` 从 `"root"` 起，
   每个 `needs_registry: true` 的面加一条）。
3. **面用哪条由 `parent:` 决定**：用父注册机那条。实测：`board/board.rs` 用 `root_object!`；
   `board/object/tile2/tile2.rs` 用 `board_object!`；`input/button/button.rs` 用 `input_object!`。
4. **`move` 会牵动它**：`parent:` 必须改（语义），别名要跟着改（自我描述）——不换编译得过，
   但那行会继续声称它挂在旧的父下。

## 2. 一次 move 牵动哪六处（在一棵真树上逐处查实）

1. **目录名 + 文件名这一对** —— stem 必须等于目录名，否则构建期 `face-layout` 拒绝。
   整棵子树跟着走（目录上的一次 `rename(2)`）。
2. **面自己的 `parent:`** —— `parent: crate::board::NODE_ID` → `parent: crate::input::NODE_ID`。
   根面的写法是特例：`parent: crate::root_node_id(crate::XIRANG_NAMESPACE)`。
3. **别名宏** —— 见上。
   **⚠️ 更正（实测）**：交接清单说"整棵被搬子树的每个面都要换" ✗ —— **只有被搬的那个根面** ✓。
   理由：一个面的别名点名的是**它自己的父级**（`alias_owner`：自身或之上最近的 `needs_registry` 面），
   而子树内部那些父级**跟着一起搬了** ⇒ 子树内部的答案还是同一个答案。
   反例检查：以 `board` 为根搬走时，`board/object/tile2` 仍用 `board_object!` ✓ 不变 ✓。
4. **点名旧路径的每一处** —— 宿主入口里的 graft 声明，**两种拼写都要**：
   类型化（`cut(crate::board::object::tile2::NODE_ID)`）与字符串（`cut ["root/board/tile2"]`）。
5. **外部计划与认领台账** —— 只报不改。一条记录的 `target` 是**身份**，而搬动改变身份 ⇒
   诚实的做法是点名"这些记录不再解析"，而不是把作者没写过的形状写回去。
6. **划分边界** —— 按 P2 拒绝。

**一次 move 就是一次身份变化**：`NodeId = hash(namespace, source path, name)` 把源码路径当输入 ⇒
面以新 id 回来，按旧 id 记账的一切都不再解析。这正是 `.xirang/moves/` 那份记录的意义：
**兼容提示，不是审计账本，只留最近 5 条** ✓（维护者原话：「记录只留最近 5 条」）。

## 3. 还欠什么（下一份工作从这里开始）

### 3.1 接口面（已查实，可直接照抄）

| 需要的东西 | 在哪里 |
| --- | --- |
| 面的清单（id / parent / module / source / owns_registry / path） | `build_method::face_views(work, &namespace)` → `FaceView`（`face_view.rs:61`） |
| 一个面的声明读取 | `run_method::authored_face(&registry, id)`（`AuthoredFace` **不含 `parent`** ✗ —— 见下） |
| 命名空间 | `mcp::registry::namespace(root)` |
| 预览 vs 落盘的工作目录 | `apply_target::Target::work_dir(root)`（`Project` ⇒ `root`，`Copy(work)` ⇒ 副本） |
| 预览/落盘共用一个写入函数 | `apply_promote::repoint_entry(work, entry, cut, applying)` 是同一种形状的范例 |
| `Outcome` 的构造 | `apply.rs:218`，字段在 `mcp` 模块内可见 |

### 3.2 为什么它是一块**新写入路径**（而不是复用执行器）

- 执行器（`edit_module_face`）**只改它生成的文件** ✗ —— 而 `parent:` 行与别名所在的文件**不是**它生成的
  （面文件由宿主作者写；只有 `apply add`/`new_project` 造的那些带 `// generated-by=XiRang`）。
  ⇒ P1 允许改手写文件，但**执行器不允许** ⇒ `move` 必须自己写、自己保证原子性与回滚。
- `AuthoredFace` **没有 `parent` 字段** ✗（22 个字段里没有它）⇒ 即使放宽执行器，patch 也表达不了"换父级"。

⇒ 这两条合起来说明：`move` 不是一次参数新增，而是**一块新的写入路径**（预览 → 逐条列出 → 落盘 →
失败回滚 → 记录）。这是它在本批里没有和其余十条一起做完的原因，而不是"来不及"。

### 3.3 拒绝族（按 P2 与既有风格：按名 + 给出路）

- `node` / `parent` 解析不到 ⇒ 点名并指向 `xirang.faces` / `xirang.explain <path>`；
- 目标父 `owns_registry == false` ⇒ 拒绝并指出一个真正的注册机面；
- 目标位置已有同名面 ⇒ 拒绝，并说明那是 `rename` 的另一件事；
- 原地踏步（同一个父 + 同一个名字）⇒ 拒绝并说明它什么都不会改；
- 面文件里找不到 `parent: …` 那一行 ⇒ **拒绝，不猜**（别名与那一行必须一致）；
- 跨 crate 认领边界（两个方向：搬出的子树被认领、目的地被认领）⇒ 拒绝并说"先改 `add_crates.rs`"。

### 3.4 五条钉子（交接清单给的，逐条对应一处牵动）

1. 搬一个**生成的面**（带 `// generated-by=XiRang`）；
2. 搬一个**手写**面（P1 的正面用例）；
3. 搬**整棵子树**并断言：**根面**的别名换了、**子树内部**的别名一个都没换（见 §2.3 的更正）；
4. **跨 crate 边界**断言归属：搬动被拒 ⇒ 切口归属**逐字未变**（拿搬之前的 `BUILTIN_GRAFT_CUTS` 对比）；
5. **记录留 5 条**：写第 6 次之后目录里只剩 5 份，且最旧的那份真的没了。

每条都要**搬前基线反证**（先对着未搬的树跑一遍：该红的那一半必须是红的）。

### 3.5 记录的形状（对齐 `graft.plan` 的既有写法）

```text
version=1
from=root/board/tile2
to=root/input/tile2
from_id=<搬前 NodeId>
to_id=<搬后 NodeId>
when=<unix 秒>
```

目录：`.xirang/moves/<序号>/move.plan`；`move clean --keep 5` 之外，落盘时**顺手**裁到 5 条
（清单原话：「默认只留最近 5 条」）。

## 5. 开工前又量到的一件事（2026-10-09 晚，写实现时撞到）

**前端不给源码偏移。** `move` 要改面文件里的 `parent:` 那一行，因此先查了能不能拿到字段的**字节区间**：

- `xirang-macro` 是 **proc-macro**（`TokenStream` 进、`TokenStream` 出）✓ —— 它拿到的 `Span` 只能用于
  **诊断**，不是源文件里的字节偏移 ✗（`macro/src/lib.rs:7` 的模块文档自己就写着"本前端拿到的是带 span 的
  作者输入"，而 span 的消费方是 rustc 的诊断）；
- kernel 的 `syntax` 解析面给出 `face.location.line` ✓（`static_plan` 就在用它），但**没有**字段值的字节区间 ✗。

⇒ **§3.3 里那条"面文件里找不到 `parent: …` 那一行 ⇒ 拒绝，不猜"不只是稳健起见，而是当前唯一的做法** ✓ ——
实现只能**按行**定位并改写，并且必须在找不到、或找到多行时拒绝 ✓。（若将来要让 move 支持多行值或同一行多条字段，
先给 `syntax` 面加一个"字段值 → 字节区间"的查询，再改这里 ✗。）

⇒ 这一条**不改变** §3 的任何设计，只是把"为什么是行级"从直觉变成了实测依据 ✓。

### ⚠️ 端到端跑出来的两个缺陷（钉子守不住、只有真项目能抓到）

**⑴ 子面的 `parent:` 行也必须改。** §2.3 的更正（"只有被搬的根面换别名"）**是对的** ✓，但它只说了别名 ✗ ——
子面自己那行 `parent: crate::panel::NODE_ID` 拼的是**父级的 Rust 路径**，而父级搬走之后那个路径不存在了 ✗。
第一版没改它们，树立刻编译不过：

```
error: NICHLink BUILD CHECK FAILED … source=shelf/panel/object/knob/knob.rs … parent declaration cannot be resolved
error[E0433]: cannot find `panel` in `crate`  --> src/shelf/panel/object/knob/knob.rs:9:20
```

修法：**在改名之前**为每个直接子面规划好它的 `parent:` 改写（拼不出恰好一次就整次拒绝 ✓），改名之后逐个写入；
所有改写都在被改名的目录里，因此回滚只需把目录改回去 ✓。

**⑵ 规划用"现在的路径"读、用"搬完之后的路径"写。** 我第一版让规划去读子面的**搬后**路径（`src/shelf/panel/…/knob.rs`）
⇒ `is not readable` ✗ ——规划跑在改名**之前**。两个路径必须分清 ✓。

**两条都写在这两个文件里**（`apply_move.rs` 的注释与本节），因为下一次改动这条路径的人会先读它们 ✓。
