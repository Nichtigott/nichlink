## 1 + 2. 切口归属：发布形状不带切口，以及"审计文本 ≠ 真实发射"

### 现场更正（先读这一段）

清单里第 1、2 条的原始描述来自两张**权威产物搞混**的读数：

- 真正被编译器看到的切口表，是生成树里的 `BUILTIN_GRAFT_CUTS`（`$OUT_DIR/generated_lib.rs`）；
- 而当时读的是 `$OUT_DIR/graft_plan.tsv`，那是**审计文本**，它当时**不做归属过滤**。

两个量器给出不同答案，于是得出"开发形状每个包带全量 ✗ · 宿主越界发射 ✗"的结论。
用编译器看的那张表逐包实测后：

| 包 | 开发形状（发射） | 发布形状（发射） |
| --- | --- | --- |
| 宿主 | 0 ✓ | 0 ✓ |
| 认领了切口所在子树的幽灵 | **1 ✓** | **0 ✗** |
| 另一个幽灵 | 0 ✓ | 0 ✓ |
| facade | 1（并集）✓ | 0 ✗（dash，二进制宿主）／2 ✓（真消费者） |

⇒ **开发形状的归属一直是对的** ✓；**发布形状的幽灵一条都不发** ✗ 成立；
而"宿主越界发射"是审计文本造成的假象 ✗，真实发射从未越界 ✓。

### 怎么钉到的

受控对照（同一份宿主、同一份声明，**只换形状**），逐包读编译器看的那张表：

```sh
# 每个包各自的权威切口表：从生成树里数 StaticGraftCut:: 条目
for out in target/debug/build/*/out; do
  pkg=$(basename "$(dirname "$out")")
  cuts=$(grep -c "StaticGraftCut::" "$out/generated_lib.rs")
  faces=$(grep -c "StaticFace::new" "$out/generated_lib.rs")
  echo "[$pkg] cuts=$cuts faces=$faces"
done
```

开发形状（`/tmp/nichlink-lab/dash`，手工项目，8 个面、1 条 typed 区间切口）：

```
[dash]                 cuts=0 faces=0      ← 宿主把整棵树交出去，一条都不发 ✓
[dash-dash-board]      cuts=1 faces=5      ← 编译切口面的幽灵发它自己那条 ✓
[dash-dash-input]      cuts=0 faces=3      ✓
[dash-facade]          cuts=1 faces=3      ← 并集 ✓
```

发布形状（同一份宿主，只重跑 `crates --release --write`）：

```
[dash]                 cuts=0 faces=0      ✓
[dash-dash-board]      cuts=0 faces=5      ✗ 应 1 条
[dash-dash-input]      cuts=0 faces=3      ✓
[dash-facade]          cuts=0 faces=0      ✗（二进制宿主，见下）
```

在**真消费者夹具** `target/real-usage/consumer`（库宿主，2 条 typed 切口）上第二份独立复现：

```
发布形状：host 0 ✓ · objects-a 0 ✗（应 2）· objects-b 0 ✓ · facade 2 ✓
```

⇒ 缺陷 1 的真实形态是**只有发布形状的幽灵丢切口** ✓，facade 在库宿主上是好的 ✓。

### 根因（两条，各自独立）

**⑴ 生成包没有切口可读。** 发布形状的幽灵 build.rs 在自己的树里跑管线
（`root = env!("CARGO_MANIFEST_DIR")`），而它的 `src/` 里只有复制过来的面文件，
**没有宿主入口**，因此 `static_graft_plan!` 一条也解析不到 ⇒ 空表。
开发形状之所以没坏，是因为它的 build.rs 把 `root` 指向**宿主目录**（读得到入口）。

**⑵ 审计文本与真实发射用了两个过滤器。** `render_lib` 用
`names_a_compiled_module` 按"本 crate 编译哪些模块"过滤，而
`write_graft_manifest` 直接收下入口声明的全部 ⇒ 每个包的 `graft_plan.tsv`
都写着宿主的整份计划 ✗。实测：input 幽灵的表里 0 条，而它的审计文件写着 1 行 ✗。

### 改法

**⑴ 让切口随生成包走（数据，不是文本）。**
新增 `build_method::HostCut`（解析器对一条 `cut(…) graft(…)` 子句的看法：
`cut`/`cut_end`/`graft`/`full`/`typed`/`cfg`/`line`/`column`）与
`run_for_partition_with_cuts` / `check_for_shape_with_cuts`。
生成器把宿主入口的**声明**（不过滤 `cfg`，那在生成包自己的构建里求值）渲染进
每个生成包的 build.rs；管线端两条路（入口、数据）终于同一个
`enable_graft_entries`，因此 `cfg` 门控只有一份实现。
规则：**本树自己有声明时入口赢**（开发形状改了计划要立刻生效），
数据只在"本树没有声明"时作答（发布形状）。

**⑵ 归属只判一次，两个消费者读同一份。**
把过滤抽成 `renderer::owners::emitted_grafts(faces, grafts, facade)`，
`pipeline` 调它一次，结果同时交给 `render_lib`（填 `BUILTIN_GRAFT_CUTS`）
和 `write_graft_manifest`（写 `graft_plan.tsv`）。

### 复验（两种形状 × 两个真项目）

开发形状（`target/real-usage/consumer`，库宿主）：

```
[host]              cuts=0 faces=2  audit=0
[objects-objects-a] cuts=2 faces=7  audit=2
[objects-objects-b] cuts=0 faces=2  audit=0
[objects-facade]    cuts=2 faces=11 audit=2
```

发布形状（同一夹具）：

```
[host]              cuts=0 faces=2  audit=0    ← 修前 0/0，一直是对的
[objects-objects-a] cuts=2 faces=7  audit=2    ← 修前 0 ✗，现在带上它的两条
[objects-objects-b] cuts=0 faces=2  audit=0
[objects-facade]    cuts=2 faces=11 audit=2
```

⇒ 每个包发射它**编译的**那些切口 ✓，且**审计文本逐条等于它发射的表** ✓。

## 3（清单外，同一条链上发现的）. 二进制宿主的发布 facade 静默用自己当宿主

### 症状

宿主是**二进制**包时，发布形状的 facade 构建**成功**，但它：

- 编译 **0 个面**（应 11 个），发射 **0 条切口**（应 2 条）；
- 而 `cargo build` 报 `Finished`，只有一句容易读漏的
  `warning: ignoring invalid dependency 'dash' which is missing a lib target`。

### 根因

facade 的 build.rs 用 `cargo metadata` 的输出做**文本扫描**找宿主：

```text
let name = format!("\"name\":{:?}", "dash");           // ← 依赖条目也叫这个名字
let at = text.find(&name)…;
let start = rest.find("\"manifest_path\":\"")…;        // ← 从那里往后第一个，是 facade 自己
```

cargo 会**忽略**没有库目标的依赖，于是 `packages` 里没有 `dash`，
第一次出现的 `"name":"dash"` 落在 **facade 自己的 `dependencies` 数组**里，
而它之后第一个 `manifest_path` 是 **facade 自己的** ⇒
`host_root()` 返回 facade 自己的目录 ⇒ 读自己的树 ⇒ 0 面 0 切口，构建成功 ✗。

### 改法

两条，各修一半：

1. **锚点正确**：改查 `"name":"<host>","version":` —— 包对象必有 `version`，
   依赖条目没有（它的字段是 `req`）。锚点错时**响亮 panic**，并给出路。
2. **生成时按名拒绝**：`plan_facade`（发布形状）问一句"宿主有库目标吗"，
   没有就拒绝并给出路（给它一个 `src/lib.rs`，或者只在开发形状里分区）。
   判据读文件系统（`src/lib.rs`，或 `[lib] path` 指名的文件），
   因为生成器在生成包存在之前、离线运行，`cargo metadata` 会因为无关原因拒绝它。
   同时把 release 包的**规划**提到**描述之前**：拒绝属于规划，
   而它过去在预览已经列出三个包之后才到来 ✗。

### 复验

```
$ nichlink crates --release --write /tmp/nichlink-lab/dash     # 二进制宿主
nichlink: add_crates: the host package `dash` has no library target, so a release facade
cannot reach its tree: cargo ignores a dependency that is only a binary, and the facade would
compile no faces and carry no cuts while still reporting success.
way forward: give the host a `src/lib.rs` (a library host with a thin binary, the shape the
examples use), or partition in the development shape
rc=1                       ← 一个字都没多打印，一个文件都没写
crates dir: No such file or directory
```

### 钉子

- `pipeline_tests::a_package_carrying_host_cuts_emits_them_and_records_the_same_rows`
  —— 数据进来的切口被发射，且审计行数**等于**表里的条数；
- `pipeline_tests::a_package_with_no_cuts_emits_none_and_records_none` —— 否定的那一半；
- `pipeline_tests::a_hand_written_entry_still_answers_for_itself` —— 手写入口仍是权威；
- `crate_release_tests::a_release_ghost_carries_the_hosts_cuts_as_data`；
- `crate_release_tests::a_release_facade_refuses_a_host_with_no_library_target`。

## 5（清单外，真缺陷，已修）. `promote` 落地后宿主编译不过

### 症状

`promote` 预览与落盘都**成功** ✓，随后 `cargo build` 死在**生成树**里：

```
error: NICHLink BUILD CHECK FAILED / NichLink 构建检查失败
       +-- phase=face-rule branch=<unknown>
       |   source=board/object/tile2/tile2.rs:11
       |   field=needs_registry
       |   expected=board/object/tile2/registry_rule/registry_rule.rs
       |   actual=no sibling registry_rule module
       `-- this face owns a registry and names no rule, so its generated module reads
           `super::registry_rule::REGISTRATION_RULE`, and this tree mounts no such module beside it
   --> …/target/debug/build/dash-…/out/generated_lib.rs:182:1
182 | compile_error!("NICHLink BUILD CHECK FAILED …")
```

### 根因

`overlay`（落地时把外部实现的字段覆盖到宿主的面上）**连 `needs_registry` 与 `registration_rule`
一起复制** ✗。那两个字段描述的是**这个面坐在哪里**，不是它字段的来源 crate：

- 拥有注册机的面从**它旁边**的 `registry_rule` 模块读规则；
- 而落地只把**一条声明**落进**一个**槽位，不搬实现的子面。

于是外部说"我需要注册机"，而宿主那个位置没有规则模块 ⇒ 生成树发射
`super::registry_rule::REGISTRATION_RULE` ⇒ 任何 crate 都编译不过 ✗。

### 改法

`needs_registry` 与 `registration_rule` **保留宿主的**（与 `module`/`parent` 同列），
并在实现自称拥有注册机而槽位没有时，在回复里**明说这件事**（不静默）——因为一次落地不搬子面，
一个面在这里要不要注册机，是**宿主那棵树**的回答。

### 复验（同一棵手工树，同一个记录）

```
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.73s
build rc=0
$ ./target/debug/dash
registered faces: 0
```

（`registered faces: 0` 是清单第 9 条的现场，与本条无关。）

### 钉子

`apply_promote_tests::a_landing_keeps_the_slots_registry_answers_and_takes_the_faces_fields`
—— 面自己的字段（`kind`/`preset`/名字）跟着实现走 ✓，槽位的两个回答留下 ✓。
反证：把两行复制改回去 ⇒ 该钉子**红**，还原后绿 ✓。

## 7. 计划里的切口把面剪在构建之外时，`check` 与构建**现在会说**

### 症状

一条切口就把构建范围收窄到它命名的子树，而**没有任何命令会提这件事**：

```
slots (3): root/board <- graft=… full=false · root/board/card · root/board/column
pruned (3): root/input · root/input/button · root/input/slider
```

上面这两行只有 `explain --overlay` 印 ✗；`check` 报 `ok`，构建报 `Finished`，
运行期从 6 个面变成 3 个 ✓（收窄本身是设计 ✓，不说才是缺陷 ✗）。

### 改法

`scope::outside_slots_note(entry, all_faces, roots)` —— 一份纯函数，
`pipeline` 在**两份清单同时在手**的那一刻（`static_plan` 之后）把它逐行打到 stderr，
因此 `check` 与构建脚本两条路径**都看得见** ✓。

输出（手工项目实测，原始输出）：

```
nichlink: the cuts in /tmp/nichlink-lab/dash/src/main.rs name the subtrees this build publishes,
so 5 of 8 face(s) are outside them and are not shipped:
board · board::object::tile_moved · input · input::button · input::slider
nichlink:   to keep `board`, declare a slot for it: cut(crate::board::NODE_ID) graft(crate::board::NODE_ID),
nichlink:   to keep `board::object::tile_moved`, declare a slot for it: cut(crate::board::object::tile_moved::NODE_ID) graft(crate::board::object::tile_moved::NODE_ID),
nichlink:   to keep `input`, declare a slot for it: cut(crate::input::NODE_ID) graft(crate::input::NODE_ID),
nichlink: `NICH_LINK_SCOPE=all` keeps the whole tree instead
```

三条要点：① **量**（5 of 8）；② **名字**（面的模块路径，读者能对上源码）；
③ **可粘贴的子句**（自嫁接——与 `promote` 落地的是同一种形式，保住面子而不需要链接外部实现）
外加一条"保留整棵树"的出路 ✓。

### 钉子

`scope_tests::the_faces_a_plan_leaves_outside_are_named_with_a_clause_to_keep_them`
—— 计数、名字、可粘贴子句、`NICH_LINK_SCOPE=all` 各断言一次；
**否定的那一半**：没有面在外面时返回 `None`（否则每次声明了切口的构建都响一声，而噪音正是真警告被忽略的方式）。

## 5. 混合来源 ⇒ 两份 toolchain：现在 `check` 按名拒绝并给出可执行的出路

### 复现（真项目，原始输出）

宿主 `/tmp/nichlink-lab/dash` 的清单改从**检出**取 toolchain，它的项目外实现 `/tmp/nichlink-lab/graft`
仍从**注册局**取 —— cargo 于是链接两份：

```text
$ cargo metadata --offline --format-version 1 | jq '.packages[] | select(.name|startswith("nichlink-"))'
nichlink-kernel    0.2.2  None                                               /home/…/nichlink/kernel/Cargo.toml
nichlink-kernel    0.2.2  registry+https://github.com/rust-lang/crates.io-index  …/nichlink-kernel-0.2.2/…
nichlink-macro     0.2.2  None                                               /home/…/nichlink/macro/Cargo.toml
nichlink-macro     0.2.2  registry+…                                         …/nichlink-macro-0.2.2/…
nichlink-toolchain 0.2.2  None                                               /home/…/nichlink/toolchain/Cargo.toml
nichlink-toolchain 0.2.2  registry+…                                         …/nichlink-toolchain-0.2.2/…
```

**宿主自己不炸** ✓（它只解析自己那一份），炸的是**分区之后的生成包**：

```text
$ cd /tmp/nichlink-lab/crates/dash-dash-board && cargo build --offline
error[E0308]: mismatched types
   --> …/build/dash-dash-board-3305599a41a1bbbe/out/generated_lib.rs:218:144
    |     expected `NodeId`, found a different `NodeId`
error[E0277]: the trait bound `nichlink_kernel::registry_core::declaration::contract::NoParts: PartsContract` is not satisfied
   --> …/generated_lib.rs:223:114
rc=101
```

⇒ 失败落在 `generated_lib.rs` 里，而那是作者改不了的文件 ✗。

### 改法

`package::duplicated_own_crates(manifest)` 从 `cargo metadata`（完整图，不是清单）里数本工作区自己
的 crate 有几份；`nichlink check` 在**管线之前**问它，>1 就按名拒绝，并给出两份各自的来源与出路：

## 4. `crates --declare --write` 写坏手写声明：**写入端与读取端都修好了**

清单把这条判给改名波，只留"读者拒绝括号不配平"这半条可先修。读端一硬，**写端立刻变成红的既有测试**
（`declaring_appends_without_disturbing_what_is_there`）⇒ 两半一起修，才有一棵绿的树。

### 复现（真项目，原始输出）

```text
$ nichlink crates --declare extra --subtree crate::input::SUBTREE --write .
-        Crate::named("dash-board").at(&[crate::board::SUBTREE]),
+        Crate::named("dash-board").at(&[crate::board::SUBTREE
+        Crate::named("extra").at(&[crate::input::SUBTREE]),
+]),
```

写出的 `add_crates.rs` 里，新 entry 落在**上一条 entry 内部** ✗。

### 根因（与清单记的**不同**）

清单说"括号不配平"。实测：**每一个括号都配平** ✓ —— 写入方只是把 `]),` 挪了位置：

```rust
        Crate::named("dash-board").at(&[crate::board::SUBTREE
        Crate::named("extra").at(&[crate::input::SUBTREE]),
]),
```

数一遍：`.at(` 与 `&[` 各开一层，后面那些 `]`/`)` 逐个把它们关掉，最后 `Shape::of(` 也被关掉 ⇒ 栈空。
真正的问题是**它不是合法 Rust**：数组里放着两个相邻的表达式
（`crate::board::SUBTREE Crate::named("extra")…`）✗。

### 改法（三处，各修一半）

1. **插入锚点按深度找** ✗→✓：`declare` 过去写 `before[list_start..].find(']')`，而在
   `Crate::named("…").at(&[…::SUBTREE])` 这样的一串条目里，**第一个 `]` 是第一条 entry 自己的**
   ⇒ 插入点落在它内部。现在用 `closing_bracket(text, open)`：一个定界符栈（跳过字符串字面量）给出
   **配平的收尾** ✓。`balanced_body` 与它共用同一个扫描器（一条规则一份实现）。
2. **插入点落在收尾括号所在行的行首** ✓（当那行除括号外只有空白时）：否则每次 `declare` 都会在
   diff 里留下一行看不见的空白改动。
3. **主体必须真的能解析** ✓：读端在取出主体之后交给 `syn::parse_str::<syn::Expr>` ——
   **配平的括号数不出语法**，而 `syn` 数得出 ✓。这同时把"写后回读"接上了：`apply_declaration_edit`
   本来就有"改动后重新读一遍，读不回来就回滚"的机制 ✓，而它过去用的正是那个宽松的读者 ⇒ 坏写入
   一路绿灯 ✗；现在同一个机制会**回滚并报出原因** ✓。

### 复验（真项目，原始输出）

```text
$ nichlink crates --declare extra --subtree crate::input::SUBTREE --write .
+        Crate::named("extra").at(&[crate::input::SUBTREE]),

$ cat add_crates.rs
use nichlink_toolchain::run_method::{Crate, Shape};
pub fn add_crates() -> Shape {
    Shape::of("dash", &[
        Crate::named("dash-board").at(&[crate::board::SUBTREE]),
        Crate::named("extra").at(&[crate::input::SUBTREE]),
    ])
}

$ nichlink check .
nichlink check: ok (dash)
```

diff 只有一行新增 ✓，文件可解析 ✓，读回来是同一个形状 ✓。

### 钉子

- `shape_decl_tests::a_declaration_with_unbalanced_brackets_is_refused` —— 夹具是**逐字取自
  那次真实运行**的坏文件（不是手写的"不配平"样本：手写的第一版**是配平的** ✗，写着写着就把洞补上了）；
- `shape_decl_tests::declaring_appends_without_disturbing_what_is_there` —— 既有的那条，读端一硬
  它就红了，写端修好它才绿 ✓（这正是"改一处共享行为要重跑全部装置"在测试层的形态）；
- `shape_decl_tests::a_quoted_brace_is_not_a_delimiter` —— 反向：合法声明里字符串含 `}` 仍要读得回来。

## 14. 面文件重命名的拒绝：现在讲**身份**，不只讲布局

拒绝原文只有布局那一半：

```
registration face is outside the `<name>/<name>.rs` layout, so the build can never compile it;
move the file to `<name>/<name>.rs`
```

而"把文件挪过去"在当前框架里**是一次改名**：`NodeId = hash(namespace, source path, name)` 把源码路径
当输入 ⇒ 旧路径烤出来的那个身份没了，按旧 id 记账的每一条 graft 记录、认领条目与插件锁都不再解析。
现在这句话跟在布局那句后面，并给出查账的命令：

```
… move the file to `<name>/<name>.rs`. That move is a **rename** as far as this framework is concerned:
`NodeId = hash(namespace, source path, name)` takes the source path as an input, so the face this build
derives is not the one the old path produced — every graft record, adoption entry and plugin lock keyed
by the old identity stops resolving, and `nichlink diff {"records": true}` lists what did
```

钉子：`pipeline_tests::a_face_outside_the_layout_is_reported_with_its_path` 现在同时断言身份那一半
（`NodeId = hash(…)`、"stops … resolving"）✓ —— 只断言布局那一半的旧版本会让这句话被再一次删掉而无人察觉。
